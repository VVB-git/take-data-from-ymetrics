# Какие параметры Метрика может отдать неверно

Имеется в виду расхождение с интерфейсом Метрики, со старыми отчётами в Figma или с админкой рекламной системы — не обязательно ошибка сервиса.

Сервис запрашивает Reporting API с `accuracy=full`, атрибуцией `last`, фильтром `utm_source` (если метка заполнена) и опционально без роботов.

## Общие условия, из‑за которых «плывут» почти все цифры

- **Роботы.** На форме по умолчанию «да» (роботы входят). В интерфейсе Метрики чаще смотрят без роботов. Сверьте тумблер, иначе визиты, отказы и конверсии не совпадут.
- **Атрибуция `last`.** Старые отчёты могли считаться lastsign, automatic или first. Смена модели двигает и визиты с UTM, и цели.
- **Семплирование.** Даже `full` на большом счётчике может вернуть `sampled`. На экране прогресса появится пометка, что данные семплированы.
- **Период и часовой пояс.** Даты берутся из формы. Если в кабинете другой пояс, границы суток съедут.

## По номерам каталога

### 8. Клики, факт

В Метрике это **визиты** (`ym:s:visits`) с фильтром метки, не клики рекламного кабинета. Расхождение с админкой почти всегда: разные боты, счётчик, окно атрибуции, отказ засчитать визит.

Не подменяйте этим показы.

### 12 / 14 / 19. Показы, охват, CPC

Из Метрики **не запрашиваются**. Это расчёт на сервере:

- показы факт ≈ клики / (CTR факт / 100) — CTR нужно вводить **в процентах** (1,2 = 1,2%);
- охват факт ≈ показы / частота факт (по умолчанию частота 4);
- CPC ≈ бюджет факт / клики факт.

Если CTR, бюджет или частоту не заполнили, в слайде стоит тире. Нельзя считать, что это цифры Метрики.

### 20–25. Глубина, отказы, время

- Порог отказа задаётся в счётчике. Другой порог — другие %.
- Глубина и время — средние по визитам среза, не по пользователям.
- Время округляется до 0,1 сек; в отчёте есть и секунды, и `м:сс`.
- Срез «другие источники» — все визиты **кроме** нашей `utm_source`, не «весь сайт».

### 26–31. Устройства

В каталог идут только ПК / смартфон / планшет, доли **перенормированы на эти три**, чтобы сумма была ~100%. TV в эти три % не входит: его доля от **всех** визитов пишется служебной строкой без номера.

Если в кабинете смотрели доли от всех устройств включая TV, цифры будут другими.

### 32–37. Возраст и пол

- Модель Метрики, не опрос. При `contains_sensitive_data` без строк API отдаёт пусто → «недостаточно данных» (порог меньше 10 пользователей в срезе).
- Корзина «младше 18» в отчёте нет: она складывается в **«не определено»**.
- Проценты считаются от **всех** пользователей среза, включая «не определено». Если раньше в Figma брали только known, доли 18–54 будут ниже.
- Пол: «не определено» в № 33–34 не входит; пишется отдельной служебной строкой, чтобы 33+34 не обязаны давать 100%.

### 38–40. Отказы / глубина / время × возраст и пол

Это визитные метрики в ячейке «возраст × пол», а не те же % что в соцдеме (там `users`). В мелких ячейках шум, нули и пропуски нормальны. Не сравнивайте ячейку «18–24 / женщины, отказы» с долей женщин 18–24.

### 41–42. Гео по post-click

- Город (`ym:s:regionCity`), не регион.
- Топ-10 по **сумме достижений выбранных целей**, last-click, не post-view.
- Если целей несколько, город с двумя целями получит сумму, не уникальных людей.
- Без выбранных целей в форме блок не считается.

### 43. % новых пользователей

Берётся `ym:s:percentNewVisitors`. Это не всегда `newUsers / users`. Определение «новый» зависит от настроек счётчика (окно, кросс-девайс).

### 46–47. Post-click прямые и ассоциированные

- Прямые: достижения цели в визитах с нашей UTM (или по всем источникам, если метки нет).
- Ассоциированные: `USER(utm_source==метка)` минус прямые. Это **не** модель ассоциированных конверсий Метрики и **не** post-view. Человек с меткой в любом визите периода попадает в USER, даже если конверсия была с другого источника.
- Итого по целям — сумма достижений, не уникальные конверсии: один человек с двумя целями считается дважды.

### 53. Факт PV конверсий

**В session Reporting API post-view нет.** Поле на форме, ввод руками / из админки. Не подставляйте сюда PC — отчёт будет врать.

### 54. Факт PC конверсий

Сумма прямых достижений выбранных целей. Не «уникальные заявки» и не Roistat.

### 56 / 58–60. ДРР и CPL

Расчёт на сервере, не Метрика. ДРР факт ≈ бюджет / (средний чек × факт PC) × 100. Это грубая оценка выручки. CPL (PV) пустой, пока не заполнен факт PV.

### 62. Клики по баннерам

Разбивка по `ym:s:UTMContent` в срезе нашей метки. Если креатив не пишется в `utm_content`, будет «нет разбивки по UTM Content» или одна куча без подписи. Это не клики баннера из рекламного кабинета.

## Что сервис сознательно не берёт из Метрики

План/факт медиаплана (7, 9–11, 13, 15–18), matching (44), цели и числа post-view (48–52, 53), Roistat (57), средний чек (61), CTR и картинки баннеров (63, 65), список слайдов (66). Их источник — админка или ручной ввод на форме.
